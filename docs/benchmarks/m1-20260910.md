# M1 baseline: 2026-09-10

M1's runtime acceptance checks passed: seven feasibility executions, seven
warmups, fourteen measured executions, and both planned profiler captures.
The offline report validates all 30 results with no accounting, replay, hash,
or cleanup errors. W4 refill throughput improved 27.1% and 28.1% in the matched
pairs; the W5 control was inconclusive. These results cover the frozen FP32
workloads described in the [benchmark guide](../benchmarks.md).

Execution commit: [`eb36183ecc980090310cdb08fbc38b2a371a0f61`](https://github.com/hsliuustc0106/vllm-lt/commit/eb36183ecc980090310cdb08fbc38b2a371a0f61),

the measured execution path or adding measurements. Use the execution commit to

The checkpoint and tokenizer are `ByteDance/Ouro-1.4B` at
`574fa66cb8bf5abdc979642d01cf2b79b16bfab1`, loaded from the prepared local copy.
Execution uses real weights in FP32 with Triton attention, greedy sampling,
full-depth prefill, and the committed [run contract](../../benchmarks/fixtures/ouro-m1-contract.json).
W4/W5 are synthetic token/depth replay, not adaptive-quality evaluations.

One reserved physical GPU 7, NVIDIA L20X, was exposed as `cuda:0`, UUID
`0e488755-d8ed-b688-81e7-8e377dc10fd5`. PyTorch was `2.13.0+cu130`, Triton
`3.7.1`, Python `3.12.13`. Both PyTorch thread counts were one; actual CPU/NUMA
placement and runtime settings are in the manifest. The same model remained
resident and each execution received a fresh engine and 6 GiB KV pool. No
shared caches or between-run cuBLAS workspaces were cleared.

Total execution, including in-reservation preparation, warmups, both diagnostic
captures, serialization and final cleanup, took 744.527 seconds under the
2-hour limit. Profiler executions took 147.666 and 438.482 seconds including
CPU trace aggregation and draining; both stayed below the 600-second guard.
These diagnostic durations are excluded from performance comparisons.

## Measured results

Each cell has exactly two measured observations. Throughput includes enqueue,
queueing, prefill, and decode. TPOT is token-weighted and excludes the first
prediction. Pairing order for each replay workload was A1/B1/B2/A2, where
A is refill and B is no-refill.

| Cell | Output tokens/s, repetitions 1 / 2 | Token-weighted TPOT, ms, repetitions 1 / 2 |
| --- | ---: | ---: |
| W1 refill, 1 × 128/64 | 17.393 / 17.565 | 56.689 / 56.072 |
| W2 refill, 8 × 128/64 | 109.840 / 109.797 | 66.348 / 66.137 |
| W3 refill, 1 × 512/32 | 14.375 / 14.291 | 56.978 / 56.999 |
| W4 refill, mixed depth | 109.551 / 107.701 | 50.407 / 51.020 |
| W4 no-refill, mixed depth | 86.179 / 84.056 | 61.582 / 63.107 |
| W5 refill, depth-four control | 88.064 / 85.866 | 64.050 / 65.769 |
| W5 no-refill, depth-four control | 86.140 / 87.725 | 61.012 / 59.821 |

W4 refill throughput improves 27.1% and 28.1% in the two matched pairs.
Its modes execute identical per-request histories and 1,127 recurrent token
traversals. Refill uses 189 recurrent batches and 153 coda batches; no-refill
uses 252 and 64. These different invocation counts are consequences of the
selected scheduler policy, with the same real gate/coda/sampling work per token.

W5 throughput ranges overlap and its two pairs disagree in direction. That
control is inconclusive. Its TPOT also illustrates why an end-to-end throughput
observation should not be relabeled a decode-latency benefit. Two observations
per mode are a bounded screen, not a statistical or general serving claim.

Measured peak allocated memory ranges from 12,228,643,328 to 12,228,708,864 bytes;
peak reserved memory is 12,247,367,680 bytes. The pool itself is 6,442,450,944
bytes. Every execution releases all requests and reserved KV pages. After final
model destruction, 32 MiB of process-local cuBLAS workspace remains; after its
final release, allocated and reserved bytes are both zero. The scheduler then
reports GPU 7 available with 0 MB used.

## Profiler attribution and next implementation

The captures contain actual GPU kernel and memcpy events. Inclusive CPU scopes
are nested and include instrumentation; they cannot be summed as independent
costs or interpreted as production GPU idle time.

| Observation | W1 evidence | W4 evidence / coverage limit |
| --- | --- | --- |
| Exact capture | Steps 2–97; 16 subsequent outputs; no prefill | Steps 2–35; 16 subsequent outputs; 640 interleaved prefill tokens |
| Repeated KV metadata | 1,536 layer calls; 6,144 HtoD copies and 6,144 matching stream synchronizations in write/attention scopes | 648 layer calls; 2,592 copies and matching synchronizations in those scopes |
| GPU kernels / copies | 74,672 / 6,448 events; summed durations 222.202 / 5.374 ms | 34,936 / 2,689 events; 288.295 / 2.338 ms |
| Attention GPU kernels | 24.670 ms, versus 401.700 ms inclusive CPU attention scope | 16.511 ms; 13.727 ms belongs to prefill, 2.784 ms to decode |
| Matrix-vector / matrix-matrix kernels | Leading GEMV groups occupy at least 112.402 ms of summed kernel duration | Prefill accounts for 233.937 ms, or 81.1%, of all GPU-kernel duration |
| Benchmark page scans | 80.329 ms inclusive, separate observer overhead | 220.106 ms; 75.394 ms is nested inside the 78.322 ms KV-finalize scope |

Correlation-ID joins attribute exactly two HtoD transfers and two stream
synchronizations to each layer's `write()`, and another two of each to
`attend()`. In W1 these write/attention metadata payloads total only 24,576 and
61,440 bytes, respectively. This supports **M2 metadata reuse once per recurrent
traversal** as the next bounded optimization. The execution source constructs
four layer-independent device metadata tensors in every physical layer.

Do not select a KV-finalize kernel rewrite from W4's inclusive CPU scope:
96.3% of it is the benchmark's page scan; actual finalize GPU kernels total
only 0.092 ms. Likewise, W4's aggregate matrix-multiplication costs include
substantial prefill and do not establish a pure decode bottleneck.

For the next metadata candidate, propose W1 end-to-end throughput improvement
of at least 10% in both matched pairs, at most 5% throughput regression on each
other frozen cell, at most 64 MiB added peak allocated memory, and at most
100 ms added engine setup per execution. Freeze the final candidate/base SHAs,
paired order, numerical checks and variation rule before its measurements.
No candidate improvement is claimed by this baseline.
