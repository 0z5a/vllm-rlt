# BF16 serving compatibility — 2026-09-12

The new completions frontend passed a bounded functional validation on one
scheduler-reserved NVIDIA L20X. The first inference after readiness and three
overlapping requests matched direct engine execution for text, prompt/completion
counts and finish reasons. Fixed-depth and adaptive-depth cases were included.
The unmodified vLLM 0.28.0 client then completed all three planned workload cells.

| Client workload | Concurrency | Requests/s setting | Successful / failed | Input / output tokens | ITL samples per response |
| --- | --- | --- | --- | --- | --- |
| Serial | 1 | infinite | 16 / 0 | 2,048 / 256 | 15 |
| Concurrent | 8 | infinite | 16 / 0 | 2,048 / 256 | 15 |
| Finite rate | 4 | 2 | 16 / 0 | 2,048 / 256 | 15 |

Every response contained exactly 16 generated tokens. The 15 ITL samples confirm
that the terminal and usage events did not add a token timing sample. Detailed
client errors are empty, and all recorded TTFT/ITL values are finite and
nonnegative. The saved files include the complete upstream timing/throughput
output and per-request generated text, counts and intervals.

These are single-pass compatibility observations, not repeated performance
comparisons or tail-latency qualification. The first HTTP feasibility requests
and each client's initial test request precede its measured workload. No
additional warmups or retries were performed. Preparation and process startup
are excluded from the client metrics. See [timing definitions](../serving.md#reuse-the-upstream-benchmark)
before interpreting them; in particular, client semaphore waiting and the
usage/`[DONE]` tail are excluded from the client's request latency.

## Source and environment

- Execution source: `355ba4e3c99914d409e2154ee579dfb06f039840`, clean tree.
- Model/tokenizer: prepared `ByteDance/Ouro-1.4B`, release revision
  `574fa66cb8bf5abdc979642d01cf2b79b16bfab1`; exact checkpoint and tokenizer file
  hashes are in the [manifest](serving-20260912/manifest.json).
- Server: PyTorch 2.13.0, BF16 model/KV, Triton attention; actual software versions,
  GPU identity, reduction flags, affinity, scheduler ownership and commands are
  recorded in the manifest. Both direct reference and server used CPU affinity
  0–7 and one PyTorch intra-op thread.
- Client: vLLM 0.28.0, tag commit
  `2cf0a6915ce544dc493a0990f2ea38d81601128a`. The installed CLI, benchmark driver
  and request parser matched the release files byte-for-byte; see the
  [source check](serving-20260912/client-source-check.json). External vLLM plugins
  were disabled with `VLLM_PLUGINS=''`.
- One model/server remained resident for all HTTP/client cells, with 512 KV
  blocks, block size 16, sequence limit 8, token budget 128, and refill scheduling.
  No shared cache was cleared. Direct preparation can populate compiled-kernel
  caches; this is not a cold-start measurement.

The direct reference preparation took 8.86 seconds. Process creation to the
first successful health response took 8.80 seconds; health returned 503 while
loading. The first actual inference was then validated before any benchmark
client readiness probe. These are individual observations with separate timing
boundaries, not startup qualification.

After the device run, final review added rejection of invalid Unicode scalar
values before tokenization, termination logging, and stronger result assertions.
Those changes have CPU validation; the device evidence above remains tied to
its recorded execution commit. The generation worker, scheduler, normal SSE
framing and valid-prompt generation contract are unchanged.
